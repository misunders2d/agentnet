# AgentNet revival — M4a: questions, tasks and the default responder

Status: M4a candidate on branch `revival/mvp`. The official A2A SDK binding
and optional local MCP tools are M4b. Not released or deployed.

## One shared inbox, one responder

Each AgentNet installation (agent home) has one inbox. Any harness on the
machine can read it with `agentnet inbox` and reply with `agentnet reply`.
Reading or marking read never makes anything run.

Messages have a signed kind: `message`, `question`, `answer`, `task`,
`result`. The kind states intent only; it grants the sender nothing.

| Received | Initial state | What happens |
|---|---|---|
| question from an approved sender | `pending` | the responder answers it (approval is re-checked when the worker picks it up) |
| question from anyone else | `held` | waits; `accept` (→ `accepted`) or `reply` by hand |
| task | `awaiting` | waits for the local user to `accept` or `decline` |
| message, answer, result | — | stored only; never triggers anything, except the first reply from the recipient of a request you sent with `--follow-up` (see below) |

```sh
agentnet responder set --harness claude --dir ~/work/project [--context notes.md] [--timeout 5m]
agentnet approve alice/laptop          # questions from alice/laptop are answered automatically
agentnet ask bob/desk "what's the deploy command?"
agentnet task bob/desk "update the changelog"
agentnet accept TASK_ID                # on bob's machine: run it
agentnet cancel ID                     # stop a running job
agentnet responder off                 # everything waits for a human
```

- The **responder** is chosen by the recipient: a supported harness, a
  working directory (its own agent instructions and settings apply, nothing
  is replaced), optional context files and a time limit. Changing it affects
  the next job; each job records the responder that ran it.
- One **worker** per installation runs inside `agentnet daemon`, one job at
  a time, each in a fresh headless harness session outside any conversation
  you have open (no focus change, no typed input, no bell). A lock file
  prevents a second daemon for the same home. The worker wakes on new
  messages, on Hub pings, and on a local owner-only socket that
  `accept`/`cancel`/`approve`/`responder` use; it never polls.
- A job is claimed atomically. Its reply and its final state are stored in
  one transaction before sending; a failed send is retried from the outbox,
  never by running the harness again.
- `reply` to a question or task takes it over in the same transaction; it is
  refused while the worker is running it (`cancel` first) and after it has
  been answered. Duplicate deliveries of a message are filed once.
- If the daemon stops while a job runs, the job becomes `interrupted` and is
  not rerun automatically (a task may already have had effects); `accept`
  retries it explicitly. Timeouts and failures are reported to the sender as
  the answer/result status.
- On Linux/macOS the harness runs in its own process group, and cancel or
  timeout kills the group. A descendant that starts its own session escapes
  this; on Windows only the harness process itself is killed.

## What the harness may do

- **Questions** run in the harness's question mode (no tools for Claude and
  Pi; restricted, not tool-free, for Codex: see the table below): the prompt
  contains the question, up to
  four earlier messages of the same conversation with that sender (followed
  through reply links in both directions, stopping at anything exchanged with
  someone else or at an unknown link), and the recipient's context files,
  with the request marked as another person's untrusted input. Attachments
  are not opened.
- `unapprove` moves that sender's questions still waiting for the worker back
  to `held`; questions you accepted explicitly stay accepted, and one already
  running may finish unless you `cancel` it.
- **Tasks** run only after `accept`, in the responder directory, with the
  harness's normal permissions: nothing is bypassed or auto-approved. In
  Claude's headless mode, tool uses that would need an interactive approval
  are refused.

## Follow-ups and human review (MEL-425/426, first slice)

**Follow-up.** `agentnet ask|task --follow-up TEXT ADDRESS BODY` stores TEXT
(at most 4 KiB) with the sent request, on this machine only. When the first
reply from that request's recipient arrives, the insert transaction records
it on the request and makes the reply a `pending` job; later replies (under
any id) and replies from anyone else start nothing. The daemon's worker runs
the responder once in question mode with TEXT, the earlier messages and the
reply, and stores the output as the reply's `detail` with state
`summarized` (shown by `agentnet inbox`). Nothing is sent back, so there is
no ping-pong, and nothing the reply asks for is run. This is a local
summary, not a multi-turn continuation of the original work: resuming the
original agent conversation is not implemented. An interrupted follow-up is
not rerun.

**Needs-human outcome.** If a responder's first output line is exactly
`AGENTNET: NEEDS-HUMAN`, nothing is sent and the item becomes `needs_human`
with the rest of the output as its detail. Any other output is an ordinary
answer, so existing plain-text responders are unchanged. `reply` or
`decline` still answer such a question or task; `accept ID` reruns it
afresh (it does not resume the earlier run), e.g. after the person added
context; `resolve ID` closes it without sending. Follow-up summaries are
never rerun this way.

**Human review.** Items waiting for the local human are `held` questions,
`awaiting` tasks and `needs_human` items: `agentnet inbox --review` lists
them without marking anything read. Reading never accepts or clears them.

**Desktop notification.** The daemon's worker checks for review items not
yet notified whenever it wakes (new message, local kick, job end, Hub ping;
a local SQLite query, no network or model call). If there are new ones it
shows one notification with a fixed title and only a count, "N requests
need your decision. Ask your coding agent to review pending AgentNet
requests.", and marks them notified in the inbox table, so pings, reconnects
and restarts do not repeat it. A new review item, or an item returning to
review for a new reason (e.g. an accepted question marked `needs_human`),
updates the count once. The notifier is started with an argument list,
never a shell, and never receives message content.

| Platform | Notifier | Evidence |
|---|---|---|
| Linux | `notify-send --app-name=AgentNet --hint=boolean:suppress-sound:true --print-id [--replace-id=LAST] TITLE BODY` (session bus and libnotify 0.7.9+); each notification replaces the daemon's previous one instead of stacking | argv checked with a stand-in notify-send; live desktop test pending |
| macOS | `osascript` with the text passed as script arguments; no replace, so bursts may stack | compiles; not run |
| Windows | `Shell_NotifyIconW` balloon (`NIF_INFO`, `NIIF_INFO \| NIIF_NOSOUND`), shown by Windows 10/11 as a banner from `agentnet.exe`; no process started and no app registration. A balloon needs a notification-area icon and disappears when the icon is deleted, so an info icon (tooltip "AgentNet") is added with the first notification, later ones replace the balloon (`NIM_MODIFY`), and the icon is removed when the daemon stops normally (a killed daemon leaves it until Windows notices). A message-only window on one locked thread owns the icon; it gets no callbacks | struct layout checked against `NOTIFYICONDATAW` (976/956 bytes); Windows CI calls the real API (success or clean failure within 10 s, then removal). Seeing a banner on a real Windows desktop is not yet verified |

If the notifier fails or is missing (headless, no session bus, no Windows
notification area, `AGENTNET_NOTIFY=off`), the items stay pending and unmarked, and the daemon
logs one line naming the count and `agentnet inbox --review`. It tries again
only when new review items arrive or the daemon restarts, not on every ping.

# M4b: standard A2A through the CLI

```sh
agentnet daemon &                                   # receives the replies
agentnet a2a serve --peer bob/desk [--listen 127.0.0.1:0]
```

`a2a serve` lets an unmodified A2A client **on this machine** talk to one
enrolled peer, using the official Go SDK (`github.com/a2aproject/a2a-go/v2`
v2.6.0) for the Agent Card and the HTTP+JSON methods. It is local A2A
interoperability over AgentNet's encrypted relay/direct delivery, not a
public A2A server: the peer never receives A2A and the Hub never sees
plaintext.

- **Access:** loopback only; every request, including the Agent Card, needs
  the bearer token in `HOME/a2a-token` (owner-only file, declared in the card
  as an HTTP bearer scheme). Other local users are not trusted. Requests are
  sent as this agent; the payload cannot choose another sender or peer.
- **SendMessage:** text parts become the body; `metadata["agentnet.kind"]`
  chooses `question` (default), `task` or `message`. `file://` parts naming
  local files are sent as encrypted attachments; other URL schemes and inline
  bytes are refused. Each call starts a new task and returns at once.
  Continuing an existing task is not supported.
- **Tasks** are views of AgentNet messages (task id = message id), kept in the
  agent's database, so they survive restarts:

  | AgentNet | A2A state |
  |---|---|
  | sent, no reply yet (queued, custody, delivered) | `SUBMITTED` (delivery state in metadata; never `WORKING`) |
  | send failed / session expired | `FAILED` |
  | reply status done | `COMPLETED` |
  | failed, timeout, interrupted | `FAILED` |
  | cancelled | `CANCELED` |
  | declined | `REJECTED` |

  The reply is the task's artifact — only a reply from the peer itself
  counts, whoever else names the task;  reply files appear as
  `agentnet://attachment/REPLY/BLOB` parts with their file names — save them
  with `agentnet download REPLY`. Tasks to the peer still need its user's
  acceptance; nothing here bypasses that.
- **Unsupported, not advertised:** `CancelTask` (answers "not cancelable":
  AgentNet cannot prove remote work stopped), `ListTasks`, streaming, push
  notifications, extended card. `GetTask` only shows messages sent to this
  adapter's peer.

Tested with the official SDK client against separate `agentnet` processes
(Hub, both daemons, adapter): card and token checks, a question and two
tasks (one with a file) submitted while the peer was offline, then answered,
completed with a file, and declined by hand; adapter restart; lookups of
messages to other peers; cancel and unsupported shapes.
