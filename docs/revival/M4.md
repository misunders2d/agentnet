# AgentNet revival — M4: questions, tasks, responders and A2A gateway

> 📜 **Historical Milestone Snapshot (M4)**: This document records the design, live evidence, and limits established during Milestone 4 (questions, tasks, review states, and A2A gateway).
> For current shipped status, operational playbooks, and verified live limits, see [`docs/HANDOFF.md`](../HANDOFF.md).
> Current release: `v0.2.1` on `main`.

## One shared inbox, one responder

Each AgentNet installation (agent home) has one inbox. Any harness on the
machine can read it with `agentnet inbox` and reply with `agentnet reply`.
Reading or marking read never makes anything run.

Messages have a signed kind: `message`, `question`, `answer`, `task`,
`result`. The kind states intent only; it grants the sender nothing.

| Received | Initial state | What happens |
|---|---|---|
| question from an approved sender | `pending` | the responder answers it (approval is re-checked when the worker picks it up) |
| question from anyone else | `held` | waits; `accept` (→ `accepted`) or `reply` by hand |
| task | `awaiting` | waits for the local user to `accept` or `decline` |
| message, answer, result | — | stored only; never triggers anything, except the first reply from the recipient of a request you sent with `--follow-up` (see below) |

```sh
agentnet responder set --harness claude --dir ~/work/project [--context notes.md] [--timeout 5m]
agentnet approve alice/laptop          # questions from alice/laptop are answered automatically
agentnet ask bob/desk "what's the deploy command?"
agentnet task bob/desk "update the changelog"
agentnet accept TASK_ID                # on bob's machine: run it
agentnet cancel ID                     # stop a running job
agentnet responder off                 # everything waits for a human
```

- The **responder** is chosen by the recipient: a supported harness, a
  working directory (its own agent instructions and settings apply, nothing
  is replaced), optional context files and a time limit. Changing it affects
  the next job; each job records the responder that ran it.
- One **worker** per installation runs inside `agentnet daemon`, one job at
  a time, in a headless harness session outside any foreground conversation
  you have open (either fresh, or resuming that conversation's native session;
  no focus change, no typed input, no bell). A lock file prevents a second
  daemon for the same home. The worker wakes on new messages, on Hub pings,
  and on a local owner-only socket that `accept`/`cancel`/`approve`/`responder`
  use; it never polls.
- A job is claimed atomically. Its reply and its final state are stored in
  one transaction before sending; a failed send is retried from the outbox,
  never by running the harness again.
- `reply` to a question or task takes it over in the same transaction; it is
  refused while the worker is running it (`cancel` first) and after it has
  been answered. Duplicate deliveries of a message are filed once.
- If the daemon stops while a job runs, the job becomes `interrupted` and is
  not rerun automatically (a task may already have had effects); `accept`
  retries it explicitly. Timeouts and failures are reported to the sender as
  the answer/result status.
- On Linux/macOS the harness runs in its own process group, and cancel or
  timeout kills the group. A descendant that starts its own session escapes
  this; on Windows only the harness process itself is killed.

## What the harness may do

- **Questions** run with the recipient's own harness setup (skills,
  plugins, MCP servers, permissions), without editing tools or new approvals
  (see the table below). The recipient's permission grants stay the
  authority: Bash commands or MCP tools their settings already allow (Claude)
  and MCP tools their Codex config auto-approves keep their effects; the
  prompt asks for no changes but is not a fence. The prompt
  contains the question, up to
  four earlier messages of the same conversation with that sender (followed
  through reply links in both directions, stopping at anything exchanged with
  someone else or at an unknown link), and the recipient's context files,
  with the request marked as another person's untrusted input. Attachments
  are not opened.
- `unapprove` moves that sender's questions still waiting for the worker back
  to `held`; questions you accepted explicitly stay accepted, and one already
  running may finish unless you `cancel` it.
- **Tasks** run only after `accept`, or under a task grant (below), in the
  responder directory, with the harness's normal permissions: nothing is
  bypassed. In Claude's headless mode, tool uses that would need an
  interactive approval are refused.

**Task grants (once / always / revoke).** `accept ID` runs one task.
`approve --tasks ADDRESS` (or `accept --always ID`, which accepts that task
and grants in one transaction) lets that sender's future tasks run without
asking, for one exact key; `unapprove --tasks ADDRESS` ends it; `approvals`
lists grants with the key and whether each still holds.
- Evidence is the key that verified each task: it is stored with the row
  (`inbox.verified_by`, schema step 12), not read from the peer table later.
  Rows stored before this have none and always wait. `accept --always`
  refuses a task not verified by the currently pinned key.
- A task starts `pending` only if a grant for its sender names that key, the
  key is still pinned and no key change is pending, checked in the insert
  transaction; the worker's claim checks all three again (grant, verifying
  key, current pin) in SQL.
- Revoke, a pending key change, trusting a different key, or regranting for
  another key move that sender's not-yet-started tasks back to `awaiting` in
  the same transaction, with a local note, so nothing sits invisible. Running
  tasks may finish (the command lists them for `cancel`); accepted-once tasks
  stay accepted. A grant never moves to a trusted new key.
- Grants affect only tasks that arrive later: waiting, failed, interrupted,
  cancelled and needs_human tasks still need `accept ID`; regranting never
  resurrects what was moved back. Question approvals are separate and
  unchanged.
- Tests: TestTaskGrantOnceAndAlways (real receive path and worker),
  TestAcceptAlwaysNeedsTaskProvenance, TestTaskGrantClaimRechecks,
  TestTaskGrantRevokeAndKeyChange, TestTaskGrantPinChangeDemotes,
  TestTaskGrantAcrossRestart, itest TestCLITaskGrantJourney (CLI, daemons and
  a stand-in responder). Mutations removing each guard fail a test.

## Follow-ups and human review (MEL-425/426, first slice)

**Follow-up.** `agentnet ask|task --follow-up TEXT ADDRESS BODY` stores TEXT
(at most 4 KiB) with the sent request, on this machine only. When the first
reply from that request's recipient arrives, the insert transaction records
it on the request and makes the reply a `pending` job; later replies (under
any id) and replies from anyone else start nothing. The daemon's worker runs
the responder once in question mode with TEXT, the earlier messages and the
reply, and stores the output as the reply's `detail` with state
`summarized` (shown by `agentnet inbox`). Nothing is sent back, so there is
no ping-pong, and nothing the reply asks for is run. This is a local
summary, not a multi-turn continuation of the original work: resuming the
original agent conversation is not implemented. An interrupted follow-up is
not rerun.

**Needs-human outcome.** If a responder's first output line is exactly
`AGENTNET: NEEDS-HUMAN`, nothing is sent and the item becomes `needs_human`
with the rest of the output as its detail. Any other output is an ordinary
answer, so existing plain-text responders are unchanged. `reply` or
`decline` still answer such a question or task; `accept ID` reruns it
afresh (it does not resume the earlier run), e.g. after the person added
context; `resolve ID` closes it without sending. Follow-up summaries are
never rerun this way.

**Human review.** Items waiting for the local human are `held` questions,
`awaiting` tasks and `needs_human` items: `agentnet inbox --review` lists
them without marking anything read. Reading never accepts or clears them.

**Desktop notification.** The daemon's worker checks for review items not
yet notified whenever it wakes (new message, local kick, job end, Hub ping;
a local SQLite query, no network or model call). If there are new ones it
shows one notification with a fixed title and only a count, "N requests
need your decision. Ask your coding agent to review pending AgentNet
requests.", and marks them notified in the inbox table, so pings, reconnects
and restarts do not repeat it. A new review item, or an item returning to
review for a new reason (e.g. an accepted question marked `needs_human`),
updates the count once. The notifier is started with an argument list,
never a shell, and never receives message content.

| Platform | Notifier | Evidence |
|---|---|---|
| Linux | `notify-send --app-name=AgentNet --hint=boolean:suppress-sound:true --print-id [--replace-id=LAST] TITLE BODY` (session bus and libnotify 0.7.9+); each notification replaces the daemon's previous one instead of stacking | verified live on desktop with real notify-send (notification ID replacement, silence hint, no duplicate on restart; visual banner confirmed) |
| macOS | `osascript` with the text passed as script arguments; no replace, so bursts may stack | compiles; not run |
| Windows | `Shell_NotifyIconW` balloon (`NIF_INFO`, `NIIF_INFO \| NIIF_NOSOUND \| NIIF_RESPECT_QUIET_TIME`), shown by Windows 10/11 as a banner from `agentnet.exe`; no process started and no app registration. During a user's quiet time (first hour after first sign-in or an OS upgrade) Windows discards the balloon although the call succeeds, so that item counts as notified. A message-only window on one locked thread owns the icon; it gets no callbacks | struct layout checked against `NOTIFYICONDATAW` (976/956 bytes); Windows CI calls the real API (success or clean failure within 10 s, then removal). If the notifier fails or is missing (headless, no session bus, no Windows
notification area, `AGENTNET_NOTIFY=off`), the items stay pending and unmarked, and the daemon
logs one line naming the count and `agentnet inbox --review`. It tries again
only when new review items arrive or the daemon restarts, not on every ping.

**Notification click (MEL-435, Linux).** When `xdg-terminal-exec` (the
freedesktop default-terminal launcher) is on the daemon's PATH, the review
notification says "Click to review it (them) with your coding agent." and
carries one fixed click command, built by the daemon from local metadata only
(its own binary, home, the responder directory and an item id; nothing a peer
wrote), as an argument list:
`xdg-terminal-exec --title=AgentNet review --dir=DIR -- <this agentnet> --home
HOME open ID` (the one waiting item) or `... open --review` (several). It is
sent two ways:
- **`omarchy-exec-argv` hint** (a JSON argument list). Omarchy's notification
  shell stores it with the popup and its history entry and runs it, as an
  argument list with no shell, when either is clicked, from the desktop
  session's own environment; it survives popup expiry, daemon restarts and
  shell restarts (source: `/usr/share/omarchy/shell/plugins/notifications`,
  `Service.qml` invokePopupDefault/removePopup, `NotificationLogic.js`
  execArgvFromHints/parseExecArgv). On a click Omarchy runs it and does not
  also invoke the action, so there is no double launch.
- **The standard `default` action** (`notify-send --action`, libnotify
  0.7.10+) for other freedesktop servers. It works only while the
  notification is live: servers drop actions when it expires or closes (in
  Omarchy a history row has no live actions), so on those servers a history
  click does nothing. notify-send stays running to report a click; the daemon
  returns once it has the notification id, so the worker never waits. At most
  one listener exists: a newer notification or daemon shutdown stops it, and a
  click it read but had not dispatched yet is dropped. If it reports no id, it
  is stopped and its error output is read only after it exited.
- A click the daemon launches itself goes through `systemd-run --user
  --collect --quiet --service-type=exec` when the daemon runs under systemd
  (`INVOCATION_ID`): the transient unit gets the user manager's current
  environment (display, the person's PATH), not the daemon's stale service
  environment, and a launcher that cannot be executed is reported. Otherwise it
  is started directly and a non-zero exit is logged. Later terminal failures are
  only in the terminal's own logs.
- `agentnet open` starts the chosen responder's harness interactively
  (`claude PROMPT`, `codex PROMPT`, `pi PROMPT`), in a new session, never a
  resumed or open one, with a prompt built from local metadata only (ids,
  sender address, kind, state; never message text): show the conversation (or
  `inbox --review`), summarize, treat peer text as information, and do not
  accept, decline, approve, reply, trust, resolve or run anything unless the
  person asks. For a received review notice it says the requests can only be
  decided on the other machine. Without a responder it prints the conversation
  or list and waits for Enter.
- The click itself changes nothing. The prompt is guidance to the agent, not a
  fence: in that interactive session the person's own tool permissions apply,
  as in any session they start.
- macOS (osascript has no click callback) and Windows (the balloon-click
  message is not handled) show the same notification without a click action.
- **Live evidence** (Linux, Omarchy shell/quickshell, kitty via
  xdg-terminal-exec, 2026-09-28, isolated hub and homes, preview build, fixture
  daemon run as a systemd transient unit with the installed service's gaps: no
  DISPLAY/WAYLAND_DISPLAY, PATH `/usr/bin:/bin`):
  - the banner carried both the hint and the action; after the popup expired
    the daemon's listener had exited and Omarchy's history entry held the exact
    argument list;
  - Sergey physically clicked the notification: a kitty window opened running
    `agentnet open --review`, listing both waiting tasks (manual responder, so

    Omarchy running the stored command. Whether he clicked the popup or the

  - a manual `systemd-run --user --service-type=exec` launch of the same
    command (not a click) opened kitty in its own scope with the display set;
    an earlier manual launch started a stand-in `claude` in the responder

**Review notices (headless machines).** A server shows no desktop
notifications, so a held question there once waited unseen. The local user can
name another agent of theirs: `agentnet review-to ADDRESS` (off by default;
nothing received can set it; the agent's own address is refused). When held,
awaiting or needs_human items enter review (including follow-ups your
responder marked needs_human, but never received notices), the worker sends
ADDRESS one plain `message` with inner `status: "review_notice"`, no
`reply_to` and no files. Its body is only the count and this agent's
address, never request text, senders or ids.
- **Once per item:** the notice is queued in the outbox in the same
  transaction that sets `review_sent` on the items it covers (schema step
  11), so restarts, retries and duplicate deliveries never repeat it. A
  failure before queueing (e.g. unknown address) leaves the items unmarked;
  they are tried again after a restart or a change of `review-to` (which
  wakes the daemon), never on pings; a later notice's count still includes
  them. Desktop notification and notice have separate bookkeeping.
  An item that returns to review (e.g. accepted, then needs_human) is
  reported again in the same run.
- **Recipient:** the exact shape (message + `review_notice` + no reply_to
  + no files; the body is never parsed) is stored as `needs_human` with a
  local explanation, so the usual count-only banner, `inbox --review` and
  session hooks show it. It is never claimed by the worker, `accept` and
  `decline` refuse it, `resolve` closes it locally, and the items on the other machine are
  unchanged. Rows of the exact notice shape are never forwarded: two agents
  naming each other cannot loop (a test mutation removing that filter loops
  at once).
- **Authority:** none moves. Any agent can send such a notice (as any agent
  can already send a question that raises a banner); it proves nothing and
  grants nothing. Deciding still happens on the machine that holds the item;
  the original senders learn nothing.
- **Compatibility:** v1 decoders accept unknown statuses, so older clients
  store a notice as an ordinary message with no banner. Both ends need a
  release with review notices; "delivered" never means a person saw it.
- **Live verification (v0.2.1, binary 611b633, CI run 36341139910 all 4 matrix jobs passed):**
  Laptop and headless clients upgraded with prior identity and history preserved.
  An awaiting task on the headless host never executed; exactly one review notice reached
  the laptop and was recorded as `needs_human` with `notified=1`. The owner visually
  confirmed the desktop notification banner; the synthetic item was declined and resolved.
- Tests: TestReviewNoticeReachesNamedAgentOnce, TestReviewNoticeNotQueuedStaysPending,
  TestReviewToRefusesSelfAndBadAddresses, TestReviewNoticeShape,
  TestReviewNoticeAgainAfterNeedsHuman, TestReviewNoticeCountsLocalFollowUps.

## Conversations and session awareness (MEL-425)

**Conversation history.** `agentnet conversation ID [--json] [--offset N]
[--limit N]` reads the existing inbox and outbox: every message linked to
`ID` through replies, both directions, with that one peer, oldest (by local
storage time, then reply depth) first. Links to other peers or unknown ids
are not followed; a visited set ends cycles a peer builds among its own
messages. The conversation is found from ids and reply links alone (covering
indexes, no message bodies read); only the requested page is loaded in full.
Each entry carries direction, kind, status, body, delivery or
response state, local follow-up summary and notes as separate fields, read
state and file metadata. Nothing is changed. Files you send are recorded
(name, size, SHA-256, blob id) in the same transaction as the sent message
(`sent_attachments`), so the record survives upload release; messages sent
before this version show none.

**Arrival order.** Each stored received message gets `inbox.arrival` from a
counter kept in `config`, assigned by an `AFTER INSERT` trigger in the insert
transaction, so every writer numbers rows, including a daemon of the previous
release still running after a newer CLI upgraded the database. Numbers are
never reused (even after deletes), do not depend on clocks or ids, and
survive `VACUUM`; a duplicate id is not stored, so it gets no number.
Existing messages are numbered from their rowid once at the upgrade, and any
rows an older writer left unnumbered are numbered in order by the next
schema step.

**Hooks.** `agentnet hooks install claude|codex` merges four handlers
(SessionStart, UserPromptSubmit, PostToolUse, Stop) running
`'AGENTNET' --home 'HOME' hook HARNESS` (single-quoted for the POSIX shell
both harnesses use on Linux and macOS; Windows is refused until its hook
shell is verified) into the harness's user-level hook file, after a backup
under a new unique name, keeping every other key and hook. A known event
whose value is not a list is refused and the file left as it was. Only
handlers with exactly the shape AgentNet writes (type, that command form
naming an agentnet executable, timeout 10) count as AgentNet's; running it
again changes nothing, and `hooks remove` takes only those out. Harness
sessions the worker starts get `AGENTNET_BACKGROUND=1`, which makes only the
AgentNet hook silent there; the user's other hooks still run.
It is never run by tests against real files. Codex skips hooks until the user
trusts them in `/hooks` (no bypass); running sessions may need a restart.
Antigravity has no verified hook contract and is not claimed.

**Pi attention (upstream Pi 0.87.1 extension API).** `agentnet hooks install
pi` writes `$PI_CODING_AGENT_DIR/extensions/agentnet.ts` (default
`~/.pi/agent`), embedded in the binary with this agentnet path and home
filled in as string literals. Only a file whose first line is AgentNet's
marker is replaced or removed, and nothing else (no backup, no temporary
file) is left in that directory, since Pi loads every file there.
- Events: `session_start` (SessionStart), `before_agent_start`
  (UserPromptSubmit; the notice becomes a custom message in that turn),
  `agent_before_settle` (Stop; one extra model request, guarded like
  `stop_hook_active`), and Idle: in `session_start` it watches the AgentNet
  home with `fs.watch` (event-driven; database writes), and when Pi is idle
  shows `ui.notify` plus a custom message with `triggerTurn: false`, so no
  model turn is started (the message is in the session for the next turn).
  The watcher closes at `session_shutdown` and after an error (for example a
  removed home); the next prompt tries again.
- Two-phase commit: `agentnet hook pi` prints `{"text", "ack"}` and records
  nothing; the extension sends `Ack` with those values once the notice is in
  the Pi session. Pi 0.87.1 adds a message sent while it is idle before
  `sendMessage` returns (`sendCustomMessage` → `_appendCustomMessage`), so
  an idle or session-start notice is acknowledged at once; the extension
  checks `isIdle()` again right before showing it, because once a run has
  started (also while the hook was being answered) Pi only queues the
  message until the turn ends, and then nothing is shown or acknowledged. A
  message returned from `before_agent_start` is added only after the
  handler returns, so it is acknowledged at its `message_end`; an
  end-of-run entry is acknowledged when it appears in
  `sessionManager.getBranch()` at the next `turn_start` or at
  `agent_settled`. While any notice is pending no other check runs, since
  acknowledging a newer one would also mark the pending one's arrivals as
  seen; a notice still unconfirmed when the run settles is dropped, so it is
  offered again, and what was deferred is checked once Pi is idle.
  `AckAttention` moves the cursor forward only and never past the newest
  arrival. Being in the session is not proof that a person read it.
- Each `agentnet hook pi` call is bounded (10 s, 64 KiB of output; then the
  child is killed and the call counts as no news), calls run one at a time,
  and session replacement or shutdown kills a running call and drops any
  result that comes back.
- `AGENTNET_BACKGROUND=1` sessions (the worker's `pi -p`) register nothing.

`agentnet hook` reads the event from stdin and answers in the documented
shape: `hookSpecificOutput.additionalContext` for SessionStart,
UserPromptSubmit and PostToolUse; `{"decision":"block","reason":…}` for Stop
(both harnesses). It opens only the local database: no Hub request, no model,
no harness. Without an enrolled home it prints nothing and creates nothing.

**Per-session cursor.** Table `attention(harness, session, pos)` holds, for
each harness session id, the last arrival that session was told about. It is
independent of read state, response state and the worker, so another
session, the human reading the inbox, or an automatic answer never hides an
arrival from a session. A session new to AgentNet gets an overview (totals,
unread, awaiting a decision, five most recent) and starts at the present;
later calls list at most eight newer arrivals, oldest first, then "N more".
Only metadata is given (id, kind, status, sender, time, "replying to your
question X", state, file count) plus how to read the text with
`agentnet conversation`; message text is never injected. The cursor moves
only after the output was written, so a failed write shows the batch again.
Stop blocks at most once per arrival and never when `stop_hook_active` is
set; user interrupts do not run Stop in either harness. Cursors unused for
90 days are dropped.

**Limits.** A session learns of arrivals only at its hook points: an idle
session is not woken (Codex documents that it cannot be; Claude's
`asyncRewake` is not used). Concurrent hook calls of one session (parallel
tool calls) can show the same arrival twice. Whether the model acts on the
note is harness and model behaviour, shown only by live runs.

## Background sessions per conversation (MEL-425)

The worker keeps, for Claude and Codex, one harness session per
conversation and mode, and resumes it for that conversation's next approved
question or accepted task. It never attaches to a session the user opened,
and it runs a session only when a new eligible job exists: saved context is
not autonomous continuation, and follow-ups remain one-shot local
summaries. Pi runs every job fresh.

- **Record.** `inbox.session_ref` (schema step 9) on the received question or
  task holds harness, mode, canonical directory (symlinks resolved), preset
  (a hash of the mode's flags and the harness binary's path, size and
  modification time; no `--version` run per job) and session id. Claude's
  id is generated and recorded before the run (`--session-id`); Codex's is
  taken from the first run's `--json` `thread.started` event and recorded
  before the answer is used. If recording fails, nothing runs (Claude) or
  the result is not used and the job ends `failed` (Codex); it is never run
  again automatically. A Codex run that reports no id keeps its answer and
  records nothing.
- **Reuse.** From the new job's own message up its reply links with the same
  peer, the first received message that recorded a session decides: it is
  resumed only if harness, mode, directory and preset match and its job
  ended `answered` (or `summarized`). Anything else (another harness or
  mode, changed flags or program, a different directory, `interrupted`,
  `failed`, `cancelled`, `needs_human`, or the job itself being rerun) starts
  a new session, logged and stated to the harness in the prompt; the search
  never continues to an older session. It must also be the session's
  **head**: the latest job that ran in it, recorded (config
  `session_head:HARNESS:ID`) in the same transaction as the job's
  `session_ref` when the job starts (Codex: when its id is captured). So a
  branch from an older message of the conversation starts fresh, whether
  the later job succeeded, failed or was cancelled, and the order jobs ran
  in (a held question accepted late) decides, not the order they arrived.
  Sessions without a recorded head are not resumed. Question and task modes
  never share a session, and tasks still run only after `accept`.
- **From the CLI.** `agentnet ask|task --reply-to ID ADDRESS TEXT` continues
  a conversation; ID must be a message sent to or received from ADDRESS
  (checked before sending).
- **Flags on resume.** Claude: the mode's flags minus
  `--no-session-persistence`, plus `--resume ID`. Codex: `exec resume ID`
  with the same flags; resume accepts no `--sandbox` or `--color`, so the
  sandbox is passed as `-c sandbox_mode="…"`. Codex runs (new and resumed)
  read the prompt from stdin through an explicit `-` and report with
  `--json`: the answer is the last `agent_message` of a completed turn in
  that event stream (the same text Codex writes to `-o`, per its exec
  source at rust-v0.157.1), read incrementally so any amount of other
  events cannot push it out. A failed turn, or a stream without a
  completed turn, is a failure even after a partial message; an unreadable
  (malformed or over 4 MiB) event voids any earlier agent message, so only a
  later readable one can be the answer; and `-o` is used only when a
  completed turn carried no agent message and nothing was unreadable. A live run left `-o` empty although Codex had answered; the
  cause was not found, so the harness's stderr for an empty answer goes to
  the daemon log only. A failed resume ends the job
  `failed` with that reason and is not retried.
- **Data.** A session's context is the harness's own data on disk
  (`~/.claude/projects/…`, `~/.codex/sessions/…`), separate from AgentNet's
  history and kept by the harness; AgentNet sets no retention for it.
- **Evidence.** Stub tests: create and resume across a daemon restart;
  duplicate delivery runs nothing; another peer, mode, harness, preset or
  directory each start a new session; a task waits for `accept`; an
  interrupted first ancestor stops the search; a rerun starts fresh; Codex id
  capture, resume flags and a missing id; failed recording. Live, before the
  code (Linux, 2026-09-27, isolated directory, synthetic prompts, four short
  calls): Claude and Codex each recovered a fact from the first call on
  resume. Claude's own init event showed no tools, no MCP servers and
  `dontAsk` on both calls. Codex's own turn records showed a read-only
  sandbox, approval `never` and restricted network on both turns; whether
  the resumed turn's read-only came from `-c sandbox_mode` or from the
  session is not distinguished, and no harness record shows the `--disable`
  features on resume (they are passed the same way as on the first run:
  `--disable` means `-c features.NAME=false`). Resuming only with the same
  preset keeps both cases within the same boundary. The shipped background
  session code was verified live on Linux at `c7b5d1a` (Claude native resume)
  and `0a73a04` (Codex JSON streaming capture and resume); skills-on question
  lookup was subsequently qualified live at `8ce73cc` / `8ed75da`.

# M4b: standard A2A through the CLI

```sh
agentnet daemon &                                   # receives the replies
agentnet a2a serve --peer bob/desk [--listen 127.0.0.1:0]
```

`a2a serve` lets an unmodified A2A client **on this machine** talk to one
enrolled peer, using the official Go SDK (`github.com/a2aproject/a2a-go/v2`
v2.6.0) for the Agent Card and the HTTP+JSON methods. It is local A2A
interoperability over AgentNet's encrypted relay/direct delivery, not a
public A2A server: the peer never receives A2A and the Hub never sees
plaintext.

- **Access:** loopback only; every request, including the Agent Card, needs
  the bearer token in `HOME/a2a-token` (owner-only file, declared in the card
  as an HTTP bearer scheme). Other local users are not trusted. Requests are
  sent as this agent; the payload cannot choose another sender or peer.
- **SendMessage:** text parts become the body; `metadata["agentnet.kind"]`
  chooses `question` (default), `task` or `message`. `file://` parts naming
  local files are sent as encrypted attachments; other URL schemes and inline
  bytes are refused. Each call starts a new task and returns at once.
  Continuing an existing task is not supported.
- **Tasks** are views of AgentNet messages (task id = message id), kept in the
  agent's database, so they survive restarts:

  | AgentNet | A2A state |
  |---|---|
  | sent, no reply yet (queued, custody, delivered) | `SUBMITTED` (delivery state in metadata; never `WORKING`) |
  | send failed / session expired | `FAILED` |
  | reply status done | `COMPLETED` |
  | failed, timeout, interrupted | `FAILED` |
  | cancelled | `CANCELED` |
  | declined | `REJECTED` |

  The reply is the task's artifact — only a reply from the peer itself
  counts, whoever else names the task;  reply files appear as
  `agentnet://attachment/REPLY/BLOB` parts with their file names — save them
  with `agentnet download REPLY`. Tasks to the peer still need its user's
  acceptance; nothing here bypasses that.
- **Unsupported, not advertised:** `CancelTask` (answers "not cancelable":
  AgentNet cannot prove remote work stopped), `ListTasks`, streaming, push
  notifications, extended card. `GetTask` only shows messages sent to this
  adapter's peer.

Tested with the official SDK client against separate `agentnet` processes
(Hub, both daemons, adapter): card and token checks, a question and two
tasks (one with a file) submitted while the peer was offline, then answered,
completed with a file, and declined by hand; adapter restart; lookups of
messages to other peers; cancel and unsupported shapes.

## Hub member list and presence (N6)

A newly enrolled agent can be found without knowing its address.

- `GET /v1/agents` (signed; revoked or unknown callers are refused) returns
  every enrolled, unrevoked agent, most recently joined first: address,
  presence and join time. Presence is the Hub's view of that agent's
  daemons: `connected` (a connection is open), `reconnecting` (all within
  their reconnect grace) or `offline`. At most 1000 are listed; `truncated`
  then says the list is incomplete. No keys, admin flags or endpoints.
- The same list is pushed on every push stream (`event: members`): on
  connect and whenever someone joins, is revoked or changes presence. A
  generation counter is read before the list is built, so a change made
  meanwhile is sent in the next list; changes in between are merged. The
  stream response carries `Agentnet-Members: 1`, which is how a daemon tells
  a Hub that lists members from an older one (no event would look the same
  as a slow one). No polling and no stored state: the Hub's presence was
  already in memory, and a daemon keeps the last list in memory.
- The daemon's view (`MemberView`): whether the Hub lists members, the last
  valid list and when it arrived, and `Current`: true only while the
  connection it arrived on is open and nothing unreadable came after it.
  Otherwise presence is unknown, as of that time. An invalid list never
  replaces a good one.
- `agentnet members` asks the Hub now and prints one line per member (this
  agent marked); an older Hub answers 404 and the command says the Hub does
  not list its members.
- Listing grants nothing: no key is pinned, no approval, grant or contact
  is created, and the first message to a listed address checks its key as
  before. The label is the admin's invite label, not a verified person;
  online means the Hub sees a daemon, not that someone is present. Every
  member can list every member (per-address presence was already visible).
- Tests: internal/hub TestMembersList, TestPresenceStateChanges,
  TestMembersPushed (merged bursts), TestMembersBounded; internal/client
  TestMembersDiscoveredAndPushed (no trust rows), TestMemberViewFollowsStream;
  itest TestCLIMembers (real binaries: discovery, presence, a daemon offline
  during a join, revocation, no trust rows). TestCLIMembersCompat, opt-in
  (`AGENTNET_COMPAT_TAG=v0.2.1`), built v0.2.1 from its local tag: this
  build's daemon and `members` with the v0.2.1 Hub (delivery works, members
  reports unsupported), and the v0.2.1 daemon with this Hub (it ignores the
  pushed lists, stays on one connection and receives). Run locally only.
- Not yet: the messenger page's list (pA).

## Human DMs: core checkpoint (persons, E0, envelope v2)

Non-executing core for human DMs (DECISIONS §2/§3.2, ARCHITECTURE §8/§9.1,
§13). Nothing here runs anything; agent participation is the next slice.

- **Person (explicit only).** `agentnet person create NAME` is the only way
  a person exists: not joining, an address, a label or an update. One per
  installation; the record (random person id, the name as the person's own
  claim, this device's address and key fingerprint) is signed by the device
  and published (`PUT /v1/person`); it appears in member lists and
  profiles. Peers pin it on first sight, verified against the device's
  pinned key (TOFU), and keep that key; a different record for a pinned
  person id or address freezes it as a conflict, never replaces it. Records
  arriving later (each members push, and the profile read before every
  send) are compared with the pinned one: only a record that verifies
  against that same key and names that device counts, so an unverifiable
  or missing record makes no conflict, and being listed pins no one. No linking, retirement,
  merge, recovery or history transfer yet; existing history stays device
  history.
- **DM root (E0).** Two person members, each bound to its pinned roster
  hash; signed by the creator's device; the conversation id is the hash of
  its canonical bytes. The creator pins its own root before its first send;
  a receiver pins it only from the creator's own device, verified by that
  key. The root travels inside the encrypted message (at most 2 KiB).
- **Envelope v2.** Its own signing domain (`agentnet-envelope-v2`); inner
  `conv`, `lid`, `root`, `sub`, `replica`, `origin` (an assertion, never
  proof), `emotion` (required on an agent's turn when sent; "no emotion
  sent" when missing on receipt) and `target` (the one execution recipient
  of a question or task). Version 1 carrying any of them is refused. The
  exact canonical bytes of persons, roots and capability records are
  documented next to their types (`internal/protocol/person.go`) with test
  vectors (`person_test.go`).
- **Capabilities.** Each daemon session publishes a signed record
  (`PUT /v1/caps`); `GET …/profile` lists the device's live sessions (or,
  when none is live, the one that connected last, kept across Hub restarts)
  with their records. A device reads conversations only if every listed
  session's record says so: concurrent old and new programs count as the
  older. Which sessions are live is the Hub's statement, not signed.
  `/v1/version` lists `features`; an older Hub lists none, and persons and
  DMs then say the Hub needs an update.
- **Admission.** A v2 message is admitted once per (verifying key, logical
  id); the same pair with other content is quarantined
  (`conflicting_duplicate`). Missing proof holds it (`proof_pending`), and a
  members push or new connection looks again at every held message, one
  page of 50 per sync, the daemon kicking its own next sync until the end
  (a new event starts over): messages that stay unprovable keep their
  place and never block later ones. Nothing polls. A person
  conflict holds it (`identity_conflict`, frozen). A question or task, a
  replica included, is stored as `conv_held`: the worker's claim excludes
  conversation rows, and accept, accept --always, reply and decline refuse
  them. Conversation rows are ordered by local arrival to the millisecond.
- **Sending.** A DM starts only when the relay and the other device support
  conversations. In an existing DM, a message the other device cannot read
  now is kept as `waiting` and released on the next members push that shows
  support; it is never sent as version 1. Sends go through the Hub (no
  direct route yet) and carry no files yet.

## Agent participation: records (S-D1, first checkpoint)

An agent enters a DM only through a *participation*: signed events, carried
in DM messages (`sub: event`), each signed by its author's device
(`internal/protocol/participation.go`, canonical bytes and vectors there).
Nothing runs yet: a request to a participation's agent is held for the
host's person (`conv_held`) like any DM question or task, and the worker's
claim excludes every conversation row.

- **Invite:** by either member's device. It names the host (a member
  person's roster device; its own responder would run the agent), the
  earlier messages of the DM that may be given to the agent (each exactly:
  its logical id and its sender's key, the pair it was admitted under;
  nothing else earlier; a logical id held twice here cannot be shared by
  id), and the member keys allowed follow-up tasks within this
  participation only. Sharing is visible to both people;
  no further approval (owner decision 2026-09-29).
- **Accept / decline:** only by the host device, after its person decided;
  receiving an invite never accepts it, and there is no standing
  auto-accept. An accept is all-or-nothing consent to exactly the invite it
  names (its hash); a host who wants less declines and may invite its own
  agent with the narrower scope. A retry sends the same signed event again,
  never a new one.
- **Dismiss:** by either person in the DM (owner decision 2026-09-29),
  following an event of the participation; it ends it for good. A new
  invite is a new participation and inherits nothing.
- **Resolution:** from the set of events held, never their arrival order,
  against the DM's persons as pinned now. Events stay append-only. An
  author that does not count here (unknown, not a member, frozen, another
  key) has no effect; an event following one not held yet waits for it. One
  host decision decides; more than one distinct decision (even two accepts)
  or two invites under one id is a conflict, which never runs. A dismissal
  that counts ends it whatever else is held. A participation is claimable
  (for the execution stage) only if active with nothing held, so a held
  dismissal already blocks it.
- **Context (read-only):** the invite note, the granted messages held here
  (matched exactly, including earlier agents' outputs), the requests to the
  participation (naming its host) and its outputs sent by the host device
  itself (an output claimed by another device is not the agent's), newest
  kept first within 64 KiB of bodies; nothing else of the DM, nothing of
  other conversations, no replicas or event records.
- **Storage:** an event is stored with its message in one step, so a
  message refused as a conflicting duplicate leaves no event behind. The
  participation id is part of a message's logical content. Bounds: 1000
  invites per DM; per participation 16 events plus 16 dismissals (so a
  dismissal always has room); 256 events waiting for an invite not held.
  No bound keeps a participation from being stopped. The first execution cut builds this fresh
  per job; a native session would only ever get the new delta.
- **Execution stage (not built):** a request from the host's own person to
  its agent is one outbox row for history plus one claimable inbox row
  carrying the job state, which the conversation view does not list twice.
- **CLI:** `agentnet dm invite [--grant LID,...] [--tasks FP,...] [--note
  TEXT] ID HOST`, `dm agents ID`, `dm accept-agent|decline-agent|
  dismiss-agent PID`, `dm ask-agent [--task] PID TEXT` (held, not run).
