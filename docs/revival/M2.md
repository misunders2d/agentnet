# AgentNet revival — M2: encrypted file attachments

Status: M2 candidate on branch `revival/mvp`, built on M1
([M1.md](M1.md)). Not released or deployed.

## Use

```sh
agentnet send --file report.pdf --file data.csv bob/desk "numbers attached"
agentnet inbox                         # lists attachments from the encrypted manifest
agentnet download --dir ./in MESSAGE_ID   # add --force to replace existing files
```

## How it works

- Each file is encrypted to the recipient with age (streaming, 64 KiB
  authenticated chunks) into the sender's private spool
  (`<home>/spool`). The spooled ciphertext is what is uploaded, so a resumed
  upload always sends identical bytes. The spool is deleted once the Hub
  holds the message.
- File name, size and plaintext SHA-256 travel only in the encrypted
  message. The signed envelope carries each file's ciphertext id, size and
  SHA-256, so the Hub cannot swap in a different file.
- Upload: reserve (size and quota checked up front), 512 KiB chunks at the
  Hub's current offset (fsynced before the offset advances), then
  "complete", where the Hub verifies size and digest and makes the file
  durable. Every step can be repeated after a lost response or restart. The
  Hub accepts a message only if every attachment is a completed upload by
  the sender for that recipient with the signed size and digest.
- Download (recipient only, and only once a message carries the file):
  4 MiB ranged requests into `<home>/downloads`, resuming a partial copy;
  the ciphertext is checked against the signed digest, decrypted to a
  temporary file next to the destination, checked against the encrypted
  manifest, and only then linked to its final name. Partial or unverified
  data never appears under the final name.
- Sender-chosen names are reduced to a plain file name (no directories,
  control or Windows-reserved characters). Existing files are not replaced
  unless `--force` is given. Nothing is opened, executed or extracted.
- Memory use is bounded by fixed buffers; a test moves a 48 MiB file
  through sender, Hub and recipient in one process and checks heap growth
  stays under half the file size.

## Limits (defaults)

| Limit | Default | Where |
|---|---|---|
| Plaintext per file | 100 MiB | client and Hub (`hub.Config.MaxFileSize`) |
| Files per message | 8 | envelope |
| Total Hub file storage | 1 GiB ciphertext | Hub (`hub.Config.StorageQuota`) |
| Incomplete upload idle time | 24 h, then reclaimed | Hub, at startup and on new reservations |

Reservations are checked and recorded in one database transaction, so
simultaneous uploads cannot exceed the quota.

## Current limitations

- **Completed files are kept forever.** There is no cleanup of delivered
  attachments yet; they count toward the quota until an operator removes
  them. Undelivered files are never deleted automatically.
- A reserved-but-unfinished upload counts toward the quota until it
  completes or is reclaimed after 24 h idle.
- If the Hub rejects a message permanently (for example, quota exceeded),
  its spooled ciphertext stays in the sender's spool.
- Downloaded plaintext is written with owner-only permissions; the local
  ciphertext copy is removed after a successful save.
- The same Hub metadata limits as M1 apply, plus file count and ciphertext
  sizes.
- Hub and client limits are not negotiated: a Hub configured below the
  client's 100 MiB default rejects larger files at reservation.
- Direct peer transfer is M3; tasks reuse these attachments later.
