# MEL-713 — "My agents" room and legacy device-messaging removal

Planned October 29, 2026. Phase 1 is implemented on branch `mel-713` (see
Progress); nothing is released.
Owner decisions and evidence: [MEL-713](https://linear.app/mellanni/issue/MEL-713).
Labels: **verified** = checked in source or read-only data this session;
**assumed** = must be confirmed before or during implementation.

## Owner decisions (October 29)

- Terminal agent-to-agent chats showing as "me" and vanishing is broken.
- Remove the legacy v1 device-message way completely. No compatibility, no
  migration: alpha data is wiped before launch.
- Own agents' work goes into one dedicated "My agents" room, one topic per job.
  A coordinating agent may bring in 2–5+ agents.
- Authority: own agents task each other freely. Other people and their agents
  need explicit confirmation unless already granted (including a grant given
  when inviting an agent into a chat).
- Chains: if person P may task my agent, that agent may freely task my other
  agents for P. If P may only ask questions, it may only ask my other agents
  questions for P, never task them.
- Old relay records stay unless the owner explicitly asks to delete them.

## Design

1. **Sender identity.** The CLI detects its harness from the native session
   environment and resolves this host's managed agent for it. Every turn is
   posted as that agent (`Origin agent:<harness>`, its PID) and shown by agent
   name and device. If no managed agent exists for that harness here, refuse
   with the exact registration command; never fall back to a person-labeled turn.
2. **"My agents" room.** An ordinary group from `CreateGroup`, one per person,
   whose only human member is the owner. Its ID travels to all own devices
   through the person-synced channel. Fallback if two devices create one at
   once: the oldest root wins and the other closes with a notice. Muted by
   default (existing per-chat mute); needs-you, blocker and failure turns
   still notify.
3. **Topic per job.** Key = native session ID, so one terminal session = one
   topic. `--reply-to` continues; an explicit flag starts a new topic. Inside
   a background run: if the cause is in the room, use the cause's topic;
   otherwise open a room topic linked to the cause, labeled "on behalf of
   <person>".
4. **Participation.** Invite the asker and each target agent topic-scoped
   (`InviteAgentInScope`); self-consent accepts own agents with no click.
   Helpers see only that topic (MEL-633 rule). Ask via `AskAgentInTopic` with
   the native origin receiver, so the answer returns to the asking terminal
   (MEL-537). Generalize `AwaitRoomReply` beyond background runs.
5. **Other person's agent.** `ask alice/desk` goes to the owner↔Alice DM
   (existing or `CreateDM`), topic per job, her agent invited topic-scoped.
   Auto-accept that invite when my person holds her question grant (for
   questions) or task grant (for tasks); otherwise it waits for her click.
   Never into my private room without an explicit invite.
6. **Chain rule.** Enforced sender-side on the coordinator's host: look up
   the cause requester's grant on the coordinator. Task grant → tasks allowed;
   question-only → the CLI refuses `task` and allows `ask`. Limit: receiving
   own devices trust the owner's human-role key, and an agent running under the
   owner's OS account can read the key. Documented, not solvable here.
7. **Other v1 producers.** Replies to v1 requests (worker, respond, headless)
   are deleted with v1 receive. Progress, proposals and follow-ups move to their
   conversation paths. Review notices (the cross-device "needs you" signal)
   become needs-you turns in the "My agents" room.
8. **App.** Delete the device-chat composer branch, `/api/send`, device-thread
   lists, "Device conversation" rows and saved-history recovery. Chats with own
   agents use the existing direct agent chat (`/api/dm/agent/ask`). Render the
   room and its topics with existing group/topic UI.
9. **Remove v1.** Delete v1 receive, worker jobs and the 38 store readers. Keep
   the tables; no new SQL step is needed before the launch wipe. The relay
   rejects new v1 submissions with an explicit update-required-class error,
   classified permanent on the client: no silent drop, no retry loop.
10. **Docs and hooks.** `cmd/agentnet/skill/SKILL.md`, help text, Claude/Codex/
    Pi hooks, DECISIONS (supersede device-conversation decisions), HANDOFF.

  device holds, else a new one. A device that has not yet received the room

  agents only.

## Messenger reference (AGENTS.md reuse rule)

Counterpart: Telegram forum topics (group + topics) and Slack channels where
bot-to-bot traffic is visible to people. AgentNet adaptation: per-topic agent
participation, which Telegram does not have. Source revision and exact flow are
not inspected yet; record them before implementing the room UI.
