## Overthinking supervision and debugging guards

- **Before code:** state the concrete user failure, one example input and expected result. Separate facts, hypotheses, proposed changes and verified outcomes. Inspect current v32 code and retained evidence before rebuilding something already implemented.
- **Root actively supervises cost and necessity.** Challenge extra fetches/scans, N+1 projections, locks, allocations, rendering, retained state, dependencies, abstractions and UI steps. Require a concrete reason for new durable state, protocol/capability/schema changes or authority rules, with a small D1 review. Append schema steps; never edit shipped ones.
- **Every task has a finite question, short agreed time bound, cheap discriminator, limited test budget and stop condition.** A failed prerequisite is a result, not permission for a chain of alternate fixtures, harnesses, probes or downloads. Return useful evidence promptly; no receipt churn, endless debate or speculative polishing.
- **After two failed causal attempts, stop the loop.** Before a third edit/run at the same unchanged failure, root and the relevant reviewer must explain the failed model and choose a genuinely discriminating next step, simplify/rewrite the wrong model or withdraw an unnecessary change. A cosmetic patch, longer timeout or lucky rerun is not progress.
- Trace normal startup, wake, retry, receipt and shutdown behavior. Withdraw patches that merely make a direct-function test nicer while the normal workflow already recovers correctly. Root must distinguish a real defect from missing fixture setup before approving product changes.
- Reuse existing qualified fixtures/build/preservation/deploy tooling. Do not build a second audit framework, serializer, cache, scheduler or guard system when a small focused test or existing path answers the question. Proof preparation must stay proportional to the risk and must not consume the release in repeated synthetic-fixture repair.
- Prefer a faithful before-fail, minimal fix and focused after-pass, then freeze the slice. Preserve failed logs and still-valid evidence. No repeated benchmarks for a favorable sample or reruns solely to turn a dashboard green.
- Before claiming progress or completion, point to the changed artifact and actual result. Compilation, cross-compilation, custody, queue admission, mock events, rendered acceptance and physical/native execution are different. Never turn a plan, received patch, platform skip or unknown tail into a pass.
